Writing a tool pack

A tool pack is a small Python file that turns functions into MCP tools your agents can call. This guide shows how to write one in the Builder, test it, and publish it, without leaving the browser.

What a pack is

Daedalus builds MCP servers from tools. A REST tool maps one API operation and needs no code. A pack tool is a Python function for everything else: combining several calls, computing a result, shaping a response, or talking to a system that is not a simple REST endpoint.

Functions live in a pack, one Python module. Packs come from two places:

OriginWhere it livesWho can change it
Built-inInside the runtime image (for example the demo pack)Nobody from the Builder; it changes with the image
ProjectA file in the project's storage, written from the BuilderAdministrators, from the pack editor

Both appear in the TOOL PACKS section of the building-blocks panel. Anyone can read their code with View code.

Create a pack in the Builder

  1. Sign in as an administrator. Authors and publishers can use packs but not write them.
  2. In the left panel, next to TOOL PACKS, click +. The editor opens with a working template.
  3. Give the pack a name: lowercase letters, digits and underscores, starting with a letter (for example hdfs_files). The name cannot be changed later.
  4. Write your functions (see Anatomy of a tool) and click Save pack. Daedalus imports the file in an isolated process and reports any problem with a line number. Nothing is saved until the file is valid.
  5. The pack now appears in the panel with its tools. Click a tool, or drag it onto the canvas, to create a tool record. Add all creates one record per function.
  6. Select the tool, click Test tool, adjust the sample arguments and run it. Then Review & publish as with any tool.
No restart is involved at any point. Saving a pack updates the palette immediately; publishing a release starts the code on the server.

Anatomy of a tool

"""One line describing the pack. It is shown in the palette."""
from factory.packs import ToolContext, pack_tool


@pack_tool(effect="read", requires_connection=False)
def hello(ctx: ToolContext, name: str, excited: bool = False) -> dict:
    """Greet someone by name. Use when the user asks for a greeting."""
    greeting = f"Hello, {name}" + ("!" if excited else ".")
    return {"greeting": greeting, "user": ctx.caller.username}
PartBecomesRules
Module docstringThe pack description in the paletteOptional but recommended
@pack_tool(...)Marks the function as a toolRequired. effect is "read" or "write"; requires_connection is True when the tool calls an API connection
Function nameThe default tool nameA valid Python identifier; the tool record's name can be changed afterwards
First parameter ctxThe ToolContextMust be named ctx. It is never part of the tool's inputs
Other parametersThe tool's input schemaAnnotated str, int, float or bool. A default value makes the input optional
Function docstringThe tool description agents readRequired. Say what the tool does and when to use it
Return valueThe structured resultAnything JSON-serialisable; a dict is best
Agents send inputs nested under body: calling hello looks like {"body": {"name": "Ada"}}. The playground prefills this shape for you.

The ToolContext

Every call receives ctx. Tools never read headers, tokens or environment variables themselves; the context carries what they are allowed to know.

MemberMeaning
ctx.caller.usernameThe user the server is acting for on this request. In local development it is development; in production it is the verified identity from the caller's token.
ctx.caller.tokenThe caller's credential when the connection forwards it, otherwise None. Do not log it.
ctx.connectionThe tool's connection record (name, base_url, auth_mode), or None for tools without one.
ctx.client(timeout=10.0)An httpx.Client bound to the connection's approved base URL, with the connection's authentication applied. Use it for every API call; it is the only path that respects the server's origin policy.
ctx.configThe JSON object from the tool's Configuration field in the inspector, for per-tool settings such as a root path or a page size.

Rules and limits

  • Imports. The standard library plus the libraries in the runtime image, notably httpx, pydantic, yaml and jsonschema. There is no pip install; ask for other libraries to be added to the image.
  • Time. A tool must finish within 8 seconds or the gateway reports a timeout to the agent. Long work belongs in smaller tools or a background system.
  • Size. A pack file is at most 64 KiB. A result is at most 1 MiB; keep results small, because agents read all of it.
  • Errors. Raise ValueError("message") for problems the agent can fix (bad path, missing permission). The agent receives {"error": "message"}. Any other exception is reported as an internal failure with its type.
  • Network. Call APIs through ctx.client() so the connection's approved origin and authentication apply. Code that opens its own connections bypasses those policies, and reviewers should treat that as a defect.
  • Side effects. Declare effect="write" for anything that creates, changes or deletes data. Write tools require explicit confirmation before a live test.
  • Determinism. Module-level code runs once when the server starts. Keep it to imports and constants; do not open connections or read files at import time.
  • Trust. Pack code runs inside the Server application with its permissions. That is why only administrators can write packs and why every save is recorded in the audit log.

Examples

Call an API and shape the result

@pack_tool(effect="read", requires_connection=True)
def open_tickets(ctx: ToolContext, customer_id: str, limit: int = 10) -> dict:
    """List a customer's open support tickets, newest first."""
    with ctx.client() as client:
        response = client.get(f"/customers/{customer_id}/tickets", params={"status": "open"})
        response.raise_for_status()
        tickets = response.json()
    tickets.sort(key=lambda t: t["created_at"], reverse=True)
    return {"tickets": [{"id": t["id"], "title": t["title"]} for t in tickets[:limit]], "total": len(tickets)}

Combine two calls

@pack_tool(effect="read", requires_connection=True)
def order_summary(ctx: ToolContext, order_id: str) -> dict:
    """Return an order together with its shipment status."""
    with ctx.client() as client:
        order = client.get(f"/orders/{order_id}")
        if order.status_code == 404:
            raise ValueError(f"Order {order_id} does not exist")
        order.raise_for_status()
        shipment = client.get(f"/shipments", params={"order": order_id}).json()
    return {"order": order.json(), "shipment": shipment[0] if shipment else None}

Use per-tool configuration and the caller

@pack_tool(effect="write", requires_connection=True)
def create_note(ctx: ToolContext, text: str) -> dict:
    """Record a note in the folder configured for this tool."""
    folder = ctx.config.get("folder", "/notes")
    with ctx.client() as client:
        response = client.post(f"{folder}", json={"text": text, "author": ctx.caller.username})
        response.raise_for_status()
    return {"created": response.json()["id"], "folder": folder}

Set the folder in the inspector's Configuration (JSON) field: {"folder": "/notes/sales"}. The same function can back several tools with different configuration.

Testing, publishing and editing

  • Test runs the tool through a private copy of the gateway and executor, so a draft never touches the live server. The result shown is exactly what an agent would receive.
  • Publish snapshots the pack source into the release. The live server then runs that snapshot.
  • Editing a pack later does not change any published server. Tools that use the pack lose their Tested status; test and publish them again to roll the new code out. Releases can be restored, snapshot included.
  • Deleting a pack is refused while any tool still uses it. Remove or reassign those tools first.
